## Mapping to the core recovery seam

The public types are defined by [design section 5](../superpowers/specs/2026-09-15-framework-agnostic-calendar-design.md#5-runtime-effects-and-transaction-recovery) and [ADR 0014](../adr/0014-reconcile-uncertain-booking-and-payment-outcomes.md).

| Core field/result                        | Required mapping                                                                                                                                                                                                                          |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RecoveryContext.operationId`            | Original client operation identity, retained in memory. The backend does not yet evidence a transport or lookup for this value. Adding a header alone supplies no guarantee.                                                              |
| `operation`                              | Original `book`, `reserve`, `confirm`, `cancel`, `reschedule` or `submit`; never reinterpret an uncertain mutation as a new reservation.                                                                                                  |
| `reservationUuid`                        | Preserve `data.uuid` from the original validated response. For a lost creation response, lookup must correlate the operation before a UUID is known.                                                                                      |
| `paymentStatus`                          | Driver observation (`not-started`, `succeeded`, `failed`, `unknown`), not a replacement for authoritative booking status. Keep the intent binding privately in memory; it is not a new field on the public context.                       |
| `{ status: 'confirmed', reservation }`   | Only return after authoritative confirmation of the original booking and validated `ReservationResponse`; payment success by itself is insufficient. Backend `synced` is an observed candidate mapping requiring deployment verification. |
| `{ status: 'pending' }`                  | Server knows the original operation remains unresolved; retain identity and block automatic mutation/payment retries. Missing lookup data is not proof of failure.                                                                        |
| `{ status: 'safe-to-retry', operation }` | Requires the reviewed lookup and operation-specific deduplication guarantee bound to the original context. No existing inspected route currently establishes this result. It never authorizes payment replay.                             |
| `{ status: 'failed', error }`            | Only a verified definitive failure with a typed error; transport timeout, 422 without authoritative classification or missing JSON must not imply that no charge exists.                                                                  |
| `{ status: 'unsupported' }`              | Default without a verified reconciliation implementation. Keep recovery visible and the identity intact.                                                                                                                                  |

Never persist client secrets, card data, tokens, attendee fields or override tokens to logs, analytics or browser storage. This release keeps opaque recovery handles in memory. Page closure/reload completion requires backend support rather than a frontend persistence promise.

## Opt-in staging harness

[`tests/staging/booking-recovery.spec.ts`](../../tests/staging/booking-recovery.spec.ts) defines the normalized observations and `BookingRecoveryStagingAdapter` interface. These fields are test observations, **not invented backend response fields**. No transport adapter ships yet because lookup/reuse/finalization contracts and a staging environment are missing.

The harness requires:

1. `ZAPTIME_STAGING_TEST_MODE=stripe-test` as explicit opt-in.
2. `ZAPTIME_STAGING_APPROVED_ORIGIN`, an approved HTTPS staging origin with no path or credentials. There is no default URL, and the known production API origin is rejected. An origin label is not proof of test mode.
3. `ZAPTIME_STAGING_ADAPTER`, an absolute path to a reviewed local `.mjs` module exporting `createStagingAdapter({ approvedOrigin })`. The module and factory must be inert until the read-only preflight. Supply secrets through the approved environment/secret mechanism, never inside the adapter source or command text.
4. `preflight()` must independently verify the actual deployment is staging and the Stripe account/objects use `livemode: false`; return the deployment revision, exact API origin and references to reviewed contract evidence. Adapter initialization and preflight must perform no mutation. Every subsequent Stripe response must also be checked for test mode.
5. The adapter implements every named `runScenario` using only evidenced paths, payloads, authentication and statuses. Use isolated synthetic attendees and test calendars. Follow status and webhook observations through approved backend access; do not substitute browser state, static result objects or mocked server responses.
6. Return opaque evidence references to access-controlled, sanitized run artifacts. Adapter exceptions, stdout and attachments must not reveal credentials, client secrets or attendee fields. `dispose()` releases local resources; any cleanup mutation requires the same documented server semantics as the tested operation.

Once those prerequisites exist:

```sh
pnpm test:staging
```

The root script invokes `playwright test --config playwright.staging.config.ts`. Missing opt-in or adapter fails explicitly; no skipped test counts as successful verification. Normal integration tests must exclude `tests/staging`. The staging configuration uses one worker, no retries, no recording of traces/screenshots/video, and a 25-minute scenario timeout to cross the source's real expiry boundary. See [Playwright configuration](https://playwright.dev/docs/test-configuration) for these runner controls.

### Scenario evidence rules

- Lost confirmation response: prove the mutation reached the backend and the client lost its response, then reconcile with the same operation/reservation/intent. Observe one reservation, one intent, one successful charge and one payment confirmation attempt.
- Mutation replay: run each operation at least twice with the original identity, after response loss and with concurrent requests. Count its domain side effects (including notifications/calendar synchronization), not merely HTTP responses.
- Intent reuse: replay payment creation without calling browser payment confirmation again. Count intents/invoices for the original reservation server-side.
- Unknown outcome: interrupt authentication/network completion and reconcile without cancellation or a second payment. Pending is acceptable for this scenario only; the page-closure completion scenario must reach confirmed.
- Page closure: close the actual browser/context before webhook processing, then observe final booking status through backend access. Server observation and webhook timestamps must be after closure. A successful browser assertion before closure does not qualify.
- Refresh/authentication: observe a hold longer than 20 minutes with a 15-minute renewal; exercise authentication and a failed/lost renewal response. Server clock simulation requires a documented backend test fixture; advancing only the browser clock cannot prove expiry safety.
- Cancellation/refunds: prove failure is definitive before cleanup; separately reconcile a paid cancellation against a reviewed refund policy, including refund count/amount and late webhook behavior.
- Authorization: original calendar can look up its operation; missing authentication and unrelated calendar tokens cannot. A fixture returning a known UUID is not an authorization test.

`runScenario` is a trusted reviewed test driver, not a proof verifier. Its assertions cannot authenticate an adapter's claims. Release reviewers must inspect adapter code, the deployment revision, fault-injection evidence and sanitized server/Stripe observations for every row. A filtered run or adapter preflight alone cannot open the release gate.
